# دستورالعمل استفاده از qpTwin برای AI Coding Agent

## هدف

ایجنت باید قبل از ایجاد/تغییر کد، معماری موجود را شناسایی کند و تغییرات را با شواهد واقعی و محدودیت‌های مدل بسنجد. هیچ ابزاری از qpTwin مجوز جایگزینی بررسی انسانی یا تست واقعی نیست.

## مراحل

1. `workspace_overview` و سپس `discover_architecture` برای فهم ساختار واقعی پروژه (بدون حدس زدن قطعی).
2. `check_architecture_policy` برای بررسی نقض مرزهای معماری؛ در حالت `UNCONFIGURED` از نبود خطا نتیجه مثبت نگیریم.
3. `analyze_change` با مسیرهای واقعی فایل‌های تغییرکرده؛ سپس `propose_validation_plan`.
4. `scan_code_risks` و `redteam_architecture_review` با سه اصل محرمانگی، جامعیت و دسترس‌پذیری.
5. برای تغییرات مرتبط با عملکرد و مقیاس‌پذیری، ابتدا مقادیر واقعی نرخ ورود/زمان خدمت را با `calibrate_from_csv` استخراج کن و سپس `simulate_capacity` یا `compare_capacity_scenarios` را اجرا کن. **داده ساختگی نباید داده واقعی معرفی شود.**
6. تغییرات را با ابزار مستقل و دارای اجازه و در یک شاخه مجزا بنویس. این MCP ابزار اجرای فرمان یا ویرایش کد ندارد.
7. تست‌ها در CI/Sandbox اجرا شوند. نتایج JUnit توسط `inspect_junit` خوانده شود. `evaluate_release` یک گزارش مشورتی است و حتی `ADVISORY_PASS` به معنای مجوز انتشار نیست.
8. خطرات باقیمانده، فرضیات شبیه‌ساز، نتایج آزمون و تایید بازبین در Pull Request مستند شوند.

## قالب گزارش PR

- درخواست تغییر و معیار پذیرش
- فایل‌های تغییرکرده و سرویس‌های تحت تأثیر
- APIها و قراردادهای مرتبط
- مشکلات معماری و امنیتی
- مفروضات شبیه‌سازی، ورودی‌های واقعی/فرضی و عدم قطعیت
- وضعیت تست‌های واقعی و محدودیت شواهد
- ریسک‌های باقیمانده و تصمیم انسانی
